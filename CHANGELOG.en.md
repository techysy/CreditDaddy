## [1.8.5] (2026-11-27)

Theme: **Four-line consolidated release — new QuWork product line + Croli line restored + AutoClaw (Zhipu / AutoGLM) fully onboarded + mirasim quota moved to the current per-credit expiry model; the Doubao daily check-in risk-control block (710010702) broken through by automating the local client, with the check-in badge given an in-progress state, its "not claimed" vs "checked in" contradiction fixed, and the whole-page re-render storm behind the post-click "flickering" eliminated; proxy-disconnect process guards completed (issue #72); test instances no longer hijack the user's panel (port-shadow fix); "unreadable ≠ missing" panel experience fix; bundled announcements fallback and staging gate closed out**.

- **Post-click UI "flickering" fixed (a quota batch no longer re-renders the whole page once per account)** (user report: after clicking a button / card / component the interface often starts flickering). The root cause is not state write-back but the **re-render scope**: the `loadQuotas` worker called `render()` after finishing **each individual** account's quota, and `render` rebuilds whole blocks via `innerHTML` — measured, one refresh round over 52 accounts was **52 full-page renders / 156 innerHTML rebuilds (~560ms)**. `.card`, `.icon-btn` and `.seg` all carry `transition`, so every destroy-and-rebuild replays the animation from scratch, which is exactly what reads as "flickering".
  - **Why a click triggers it, and why it happens "often"**: click actions are followed by `loadAccounts()`, and `loadAccounts` ends with a `loadQuotas()` call; on top of that the 2-minute quota timer and the `visibilitychange` catch-up when returning from the tray/background take the same path — so it flickers without clicking, and definitely flickers after clicking.
  - **Fix**: the worker loop no longer paints; a single `render()` runs after the whole batch settles via `Promise.all`. A batch superseded by a newer one does not paint either (avoiding interleaved renders). Not painting mid-batch is acceptable — account rows already show a "reading credits…" placeholder and land once, a few hundred ms later. Measured: the same round is now **1 render / 3 rebuilds (~240ms)**.
  - **Also verified there is no self-feeding loop**: `render` / `renderProd` / `renderDash` / `cardHtml` never call `loadQuotas` / `loadAccounts` / `refreshAccountList`, so there is no "render → triggers refresh → renders again" cycle; the panel has no ResizeObserver / MutationObserver either. The remaining `.then(render)` after single-account actions merely paints one extra time alongside the batch's own render and does not constitute a storm, so it was left alone.
  - **This is a separate problem from the check-in badge entry below**: the loading state is a state write-back issue, the flickering is a re-render scope issue — each confirmed and fixed on its own, not merged into one conclusion.
  - Regression: `scripts/panel-boot-smoke.cjs` gains an assertion that one `loadQuotas` round performs **at most 2** full-page renders (counted via a wrapper). Verified red against the unfixed code (30 accounts → reported 30 renders) and green at 1 after the fix — not a vacuous assertion.

- **Doubao daily check-in broken through the client-side risk control (code 710010702)**:
  - **Root cause**: Doubao's server enforces native-client signing and behavioural environment checks on the first check-in of the day (`bdticket.dll` TicketGuard, `metasecml.dll` and `bdms` anti-cheat telemetry) — a pure third-party HTTP request is recognized by the risk control and returns `code: 710010702` no matter how many headers/cookies/device fingerprints it carries. This is not an expired credential; re-logging in does not help.
  - **Approach (`checkinDoubaoViaLocalClient`, new in `src/doubaoLocal.js`)**: switch to the local Chromium DevTools Protocol (CDP) and click the button **inside the real client context** — first probe whether the debug port (default `127.0.0.1:19222`) is ready, and if not launch Doubao with `--remote-debugging-port` plus the existing `--user-data-dir`, polling up to 15s; then `Runtime.evaluate` locates the "Check In" button coordinates and `Input.dispatchMouseEvent` sends a real mouseMoved / mousePressed / mouseReleased sequence, with `Runtime.evaluate` re-verifying the result afterwards. All signing and security-stack work is done by the official client itself — CD forges no device identity.
  - **Graceful degradation (the key trade-off)**: `checkinDoubao` only probes the local client and switches to automation once it hits 710010702; when the client is already running in the foreground (so a debug port cannot be added) it **never force-kills the window the user is working in**, and instead returns actionable guidance — click "Check In" in the Doubao window, or exit the client and let CD launch it. Only an explicit `allowRestart:true` closes and relaunches it. Automation failures report honestly by stage (CDP debug mode start timeout / Doubao chat page not found / "Check In" button not found / client did not confirm the check-in result); success goes through the existing `+200 quota` persistence path. Non-Windows platforms and an explicit `localFallback:false` never take this route.
  - **i18n and regression**: +6 entries in each of the four dictionaries (guidance plus the four failure states); two new cases in `test/doubao.test.js` (710010702 → automation succeeds and writes back; client running → returns manual/exit guidance without killing the process). The CDP channel is isolated with the `_setCdpForTests` injection stub, so tests never launch the real client.
- **Account-session check-in badge fixed: explicit in-progress state, "not claimed" no longer contradicts "checked in"** (user report: the log already printed "Doubao re-probe OK (2200 pts total, checked in)" while the account row still showed "Not claimed", making it look as if check-in never worked). Two independent root causes, each now pinned:
  - **A re-probe that reads "already checked in" upstream must land in account state**: the Doubao branch of `reprobeCookieAccount` previously only wrote `checked_in_today` into the log — the account row kept `lastResult = null` and nothing went into `qoderDailyDone`, so the panel's `statusOf` could only fall through to the "Not claimed" default. Now, when upstream says checked in, it persists `lastResult={status:'already', amount: upstream reward, streakDays: consecutive days}`, fills `lastCheckin`, and writes the account's business day into `todayDone` using the same convention as the check-in round. **It only writes when checked in** — an "unsigned" reading must not backfill `failed`, which would wipe a genuine failure result (a regression case guards exactly this).
  - **`todayByProduct` in /api/status now includes doubao and quwork**: the badge compares `todayDone[id] === todayByProduct[product]`, and when the key is missing it falls back to `state.today` — Qoder's **10:00** day boundary — while the check-in round persists using each provider's **00:00** boundary. Every day between 00:00 and 10:00 the two necessarily disagree, so even with the upstream already signed and the result persisted, the badge still could not flip to "claimed today". This is the second half of "conflicting copy that never takes effect", independent of the first.
  - **In-progress state made visible**: while `state.busy[id]` is set, `statusOf` returns "Checking in..." directly (the button spins at the same time) instead of leaving the static "Not claimed" between the click and the response — the Doubao client-automation channel takes several seconds, and with only the button moving while the badge stayed frozen the user could not tell the system was working, left waiting for a toast that vanishes in an instant.
  - Regression: a new end-to-end case in `test/doubao.test.js` (in-process daemon + stubbed fetch, never hitting the real upstream) — after a re-probe the account row lands `already`, `todayDone` is filled, the doubao day boundary in /api/status matches what was persisted, and an unsigned reading preserves the previous result; `scripts/panel-boot-smoke.cjs` gains four badge-state assertions (Not claimed / Checking in... / claimed today / yesterday's record must not stay "claimed"). Both were verified red against the unfixed code (doubao 19/1, smoke 1 assert), so they are not vacuous assertions.

- **Proxy-disconnect no longer crashes the daemon (issue #72, PR #73 + PR #74)**: the "no one handles 'error' → Node exits the process with an Unhandled 'error' event" hazards in `fetchViaProxy()` of `src/zcodeClient.js` are all closed — ① the streaming `PassThrough` (when the upstream cuts the body mid-stream, `pass.destroy(err)` emits 'error' before the caller reads the body; 1.8.3 crashed 3 times online, the longest outage 19 hours, and 10Router's zcode/trae/minimax-free channels all became `ECONNREFUSED 127.0.0.1:47860`); ② the `tlsSocket` before the CONNECT tunnel is handed to `https.request` (same window in the same function, the 2026-10-05 crash the reporter remembered was here); ③ the bare socket resolved by `connectTunnel()` — between the CONNECT success and the TLS takeover there is an `await` microtask window where a proxy disconnect also crashes the process (PR #74). - **Current-account misalignment after Qoder switching (the vanishing switch button)**: toggling between international / domestic channels left the panel's "client current" marker disagreeing with the actual login — `/api/status`'s `qoderCurrent` compared by uid only with a 60-second cache. The observed path: the client silently refreshes its token (same uid, new token), and uid comparison against "multiple records with the same uid" mispicked another record as current — the new account showed no badge and the switch-button visibility logic went wrong, which the user saw as "the switch button disappeared after switching". Now aligned by the **token decoded from `auth.v1.dat`** (uid fallback), with the cache cleared immediately after a successful switch; the panel's `isClientCurrent()` judges by id. Regression: `test/qoder-current-token.test.js` (which also fixed two environment dependencies that redened CI — DPAPI key creation deferred into the test body, and closing the log archive stream on teardown).
- **Qoder switch failures now point at the real cause**: the old error "credential file missing (client may be uninstalled or moved directories)" mislabeled the most common case — the client signed out and deleted `auth.v1.dat` — as a moved directory, sending users hunting for a directory that was never the problem. Now the detection result drives the guidance (installed → sign in inside the client and re-import; not installed → install and sign in first), and the message names the account and channel.

### ✨ New

- **Qoder auto-relaunch after switching**: a forced switch closes Qoder first, but the flow used to stop at "please reopen" — users had to hunt for the shortcut themselves. - **ZCode pending grants shown as "Pending"**: activity grants only enter the balance at `effective_at` (e.g. ZCode 1024 Dev Day's 300M + 200M), which used to render as "0 / 500M remaining" — looking like lost quota. With everything pending the main row now reads "Pending 500M tokens · activity name · arrives HH:MM" with a dashed bar; when partially active, a pending line appends under the remaining row. Backend adds `pendingTotal` / `pendingAt` and per-entitlement `planName` (so users know which activity issued it).
- **10Router "Cookie sessions" became "Account management"**: account sync used to sit at the bottom of the "10Router connection settings" dialog where nobody found it, and cookie sessions had their own button. The toolbar's "Account management" dialog now holds both — account sync (push local Qoder / WorkBuddy as upstream connections, with the panel-password field for the OAuth channel) and web sessions (Token Harbor etc. cookie capture). The duplicated sync block in the settings dialog and the old dialog's dead code were removed; the free-quota page's "Sync to 10Router" remains one-click-both (connections + quota cards).
